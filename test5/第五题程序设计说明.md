# 第五题：二自由度舵机云台 —— 程序设计说明

> 平台：STM32F103C8T6（蓝丸）× 2 · HAL 库 + STM32CubeMX + CMake/arm-none-eabi-gcc
> 实时内核：FreeRTOS（CMSIS-RTOS V2 封装）
> 工程位置：`test5/master`（主控端）与 `test5/slave`（舵机执行端）

---

## 1. 题目要求与实现对照

| 题目要求 | 实现方式 | 代码位置 |
|---|---|---|
| （1）分成**舵机执行端**和**主控端**两个模块，各一套程序，之间用**无线通信** | 两块 STM32F103C8T6；主控端 = 电位器 + MPU6050 + HC-05；执行端 = 2×SG90 + HC-05。两套独立工程，通过 **2 个 HC-05 蓝牙模块**透明串口传输自定义协议帧 | `master/`、`slave/` 两套工程 |
| （2）两个电位器控制云台：一个水平、一个俯仰 | 电位器分别接 PA1(ADC1_IN1) / PA4(ADC2_IN4)，两个 ADC 各自独立单通道连续转换，任务里取平均+一阶低通后映射成 0～180° | `master/Core/Src/knob.c` |
| （3）陀螺仪模拟姿态：插在面包板上，水平旋转/上下俯仰时云台跟随 | GY-521(MPU6500/MPU6050) 接 PB6/PB7，**软件 I2C（GPIO 位操作，约 100kHz）**。水平旋转用**陀螺仪 Z 轴积分**，俯仰用**陀螺积分 + 加速度计互补滤波**；角度 1:1 映射到云台 | `master/Core/Src/attitude.c`、`mpu6050.c` |
| （4）两种控制方式写在**同一个工程**里，可**实时切换** | 主控端 PA0 按键切换，20ms 扫描 + 60ms 消抖；切换结果放进协议帧的 MODE 字段，从机按同一帧解析，**舵机端不需要任何操作** | `master/Core/Src/app.c`（KeyTask、SendTask） |
| （5）使用 **FreeRTOS** 完成开发 | 主控端 6 个任务、执行端 5 个任务，用消息队列/互斥锁/`osDelayUntil` 周期调度 | 两个 `Core/Src/app.c` |

## 2. 系统总体方案

```
        【主控端 / 手柄端】                          【舵机执行端】
  ┌──────────────────────────────┐          ┌──────────────────────────────┐
  │ 电位器1 ──PA1(ADC1)          │          │                              │
  │ 电位器2 ──PA4(ADC2)          │          │   TIM3_CH1(PA6) ──> SG90 水平 │
  │ MPU6050 ──I2C1(PB6/PB7)      │          │   TIM3_CH2(PA7) ──> SG90 俯仰 │
  │ 按键    ──PA0                │          │                              │
  │ LED     ──PC13               │          │   LED ──PC13                 │
  │                              │          │                              │
  │ USART1(PA9/PA10) ─ HC-05 ────┼── 无线 ──┼── HC-05 ─ USART1(PA9/PA10)   │
  │ USART2(PA2/PA3)  ─ 调试串口  │  蓝牙    │   USART2(PA2/PA3)  调试串口   │
  └──────────────────────────────┘          └──────────────────────────────┘
```

- 两个 HC-05 事先用 AT 指令配成一主一从并配对，配对成功后它们对单片机来说就是**一根无线串口**，所以两边代码里都只需当成普通 USART 用。
- 主控端每 **20ms** 发一帧（9 字节）；执行端收到即更新目标角度。
- 执行端 **200ms** 收不到帧就判为失联，舵机**保持在当前位置**（不乱动，比"回中/松开"安全）。

### 3.3 舵机执行端接线（逐根线）

```
             ┌──────────── 降压模块 (IN 12V / OUT 5V ≥2A) ────────────┐
             │  OUT+  ──┬───────────────────────────────┬── 舵机1 VCC(红) ── 舵机2 VCC(红)
             │          │  (第1路，就近并 470µF+0.1µF)   │
             │          └───────────────────────────────┘
             │  OUT+  ──── (第2路，单独一根) ──────── 蓝丸 5V          HC-05 VCC
             │  OUT-  ────┬──── 舵机1/2 GND(棕) ──── 蓝丸 GND ──── HC-05 GND ──── USB-TTL GND
             └────────────┴──── ★ 所有 GND 都汇到这一个点（星形共地）★
```

**A. 电源部分**

| # | 从 | 到 | 说明 |
|---|---|---|---|
| A1 | 降压 `OUT+`（第1路） | 舵机1 红线(VCC) + 舵机2 红线(VCC) | 这一路**只带舵机** |
| A2 | 同一路舵机电源两端 | 470µF 电解 + 0.1µF 瓷片 | 电解长脚接 +5V、带条纹脚接 GND，耐压 ≥10V |
| A3 | 降压 `OUT+`（第2路，单独一根线） | 蓝丸 `5V` 脚 | 板载 AMS1117 降到 3.3V 给 MCU |
| A4 | 降压 `OUT-` | 舵机 GND + 蓝丸 `GND` | **所有 GND 汇到一个点**，不要串成一长串 |
| A5 | 降压 `OUT+` | HC-05 `VCC` | 模块板上有 LDO，接 5V |
| A6 | 降压 `OUT-` | HC-05 `GND` | |

**B. 舵机信号**

| # | 从 | 到 | 说明 |
|---|---|---|---|
| B1 | 水平舵机 橙线(信号) | 蓝丸 `PA6` | TIM3_CH1 = `SERVO_CH_PAN`，装在底盘、转整机的那个 |
| B2 | 俯仰舵机 橙线(信号) | 蓝丸 `PA7` | TIM3_CH2 = `SERVO_CH_TILT`，装在水平舵机支架上的那个 |

> SG90 线序一般从左到右是 **棕(GND) / 红(+5V) / 橙(信号)**，部分批次是黑/红/黄；以"中间那根是电源"为准。

**C. 蓝牙 HC-05（从机角色）**

| # | 从 | 到 | 说明 |
|---|---|---|---|
| C1 | HC-05 `TXD` | 蓝丸 `PA10` | USART1_RX，**交叉接** |
| C2 | HC-05 `RXD` | 蓝丸 `PA9` | USART1_TX |
| C3 | HC-05 `VCC` / `GND` | 见 A5 / A6 | |
| C4 | HC-05 `KEY`/`EN` | **悬空** | 只在进 AT 模式时接高电平（3.3V） |

**D. 调试串口（USB-TTL，可选但建议接）**

| # | 从 | 到 | 说明 |
|---|---|---|---|
| D1 | USB-TTL `TXD` | 蓝丸 `PA3` | USART2_RX，交叉 |
| D2 | USB-TTL `RXD` | 蓝丸 `PA2` | USART2_TX |
| D3 | USB-TTL `GND` | 蓝丸 `GND` | |
| D4 | USB-TTL `VCC`/`5V` | **不接！** | 接了会与降压 5V 倒灌 |

**E. 烧录（ST-Link 克隆棒）**

| # | 从 | 到 | 说明 |
|---|---|---|---|
| E1 | ST-Link `SWDIO` | 蓝丸 `PA13` | |
| E2 | ST-Link `SWCLK` | 蓝丸 `PA14` | |
| E3 | ST-Link `GND` | 蓝丸 `GND` | |
| E4 | ST-Link `3.3V` | **不接** | 板子已由降压供电，避免两个 3.3V 源顶在一起 |
| E5 | 蓝丸 `BOOT0` 跳线 | 跳到 `0` | 运行模式（烧录走 SWD，不用改跳线） |

**F. 不需要接的**

- LED 不用外接：`PC13` 就是板载蓝灯（低电平点亮），程序已驱动（慢闪=通信正常、快闪=失联）；
- 舵机端**没有电位器、没有 MPU6050**（这两样都在主控端）。

**G. 上电前检查清单**

1. 万用表量降压输出 = **5.0V**（可调降压调错档会直接烧板）；
2. 舵机电源线与信号线没有插错（中间那根是电源、不能插到 PA6/PA7）；
3. 所有 GND 已连到同一点（**共地**是必须的）；
4. USB-TTL 的 `VCC` 悬空、ST-Link 的 `3.3V` 悬空；
5. `BOOT0 = 0`；
6. 上电后：LED 快闪 = 失联（正常，主机还没上电），两个舵机停在中位 90° 不动。

**H. 三个容易出问题的点**

- **舵机电流不要走面包板**：1A 级别电流过面包板簧片会发热掉压，舵机电源线直接从降压端子引；
- **判据**：两个舵机快速往返时量蓝丸 `5V` 脚，低于 **4.5V** 就是供电不够 → 换粗线 / 加大电容 / 给单片机单独一路电源；
- **方向不对**：水平/俯仰整体反了 → 直接对调 `PA6`/`PA7` 两根信号线；只是某个轴转向相反 → 改 `slave/Core/Src/servo.c` 里该通道的角度映射。

### 3.4 供电注意（很重要）

**（1）舵机必须独立供电**

- **舵机不要用 ST-Link 的 3.3V 或板子的 3.3V 供电**：SG90 堵转电流可达 1A 以上，会把 MCU 拉复位。用 5V/≥2A 的独立电源给舵机。
- 舵机电源与单片机 **必须共地**，否则 PWM 信号没有参考电平，舵机会乱抖。
- 舵机电源入口并 **470µF 电解 + 0.1µF 瓷片**，抑制舵机启停造成的电压跌落。
- 若舵机一转单片机就重启，99% 是供电问题，不是程序问题。

**（2）单片机可以由同一路降压 5V 供电**

蓝丸的 `5V` 引脚就是板载 AMS1117-3.3 的输入，接降压模块的 5V 输出即可（板子自己降到 3.3V 给 MCU）。注意：

- 上电前**先用万用表量降压输出**确实是 5.0V（可调降压模块调错档最容易烧板）；
- **不要同时插 USB 和降压 5V**：蓝丸的 5V 脚与 USB VBUS 之间只有一个二极管（个别克隆板甚至是直连），两个电源会互相倒灌。用降压供电时，USB-TTL 的 **VCC/5V 脚必须悬空**，只接 TX/RX/GND；
- 在降压模块的端子上**分两路走线**：一路 → 舵机（就近并 470µF+0.1µF），一路 → 单片机 5V 脚。不要从舵机插针上再串一根线给 MCU；
- 判据：两个舵机快速往返时，量单片机 5V 脚，**低于 4.5V 就有欠压复位风险**。想更稳就让单片机单独用一路电源（另一路降压 / 充电宝 / ST-Link 的 3.3V 只带 MCU 约 50mA 足够），**只要共地**即可；此时 ST-Link 的 3.3V 不要再接；
- **烧录时 ST-Link 只接 SWDIO / SWCLK / GND 三根**（板子已由降压供电，避免两个 3.3V 源顶在一起）；
- 舵机信号线是 3.3V 的 PWM，SG90 认这个高电平，**不需要电平转换**；HC-05 的 TXD 输出 3.3V 电平，直接接 MCU 的 RX 也是安全的。

**（3）调试串口（USB-TTL）接不接**

- **不接也能跑完全部功能**：从机端 LED 慢闪 = 收到帧、快闪 = 失联，光看灯就能判断无线链路通不通；
- **但建议接上**：接上才能看到 `LINK / AGE / OK / ERR / CMD / ACT`，云台不动时能一眼分清是"没收到帧"、"收到了但角度不对"还是"失联保持不动"；
- 接法：USB-TTL 的 `TXD → PA3 (USART2_RX)`、`RXD → PA2 (USART2_TX)`、`GND → GND`、**VCC 不接**；串口助手 115200 8N1；
- **主控端更建议接**：陀螺仪轴向标定必须看串口里的 `RAW A ax ay az G gx gy gz`，不接没法标定轴向；
- 只有一根 USB-TTL 时：先接主控端完成轴向标定，再接到从机端看链路状态。

### 3.5 关于"GY-521 竖直插在面包板上"

题目要求把陀螺仪插在面包板上、拿起面包板做动作。模块竖直插的时候，**模块自身的坐标轴和面包板的"竖直/水平"并不一致**，所以程序里把三个陀螺轴、加速度轴都做成了可配置的宏（`master/Core/Inc/attitude.h` 顶部）：

```c
#define ATT_YAW_AXIS     2     /* 0=gx 1=gy 2=gz —— 面包板"水平旋转"对应哪个轴 */
#define ATT_YAW_SIGN     (+1.0f)
#define ATT_PITCH_AXIS   1     /* 面包板"上下俯仰"对应哪个轴 */
#define ATT_PITCH_SIGN   (+1.0f)
#define ATT_ACC_UP_AXIS  2     /* 加速度计：哪个轴朝上 */
#define ATT_ACC_FWD_AXIS 1     /* 加速度计：哪个轴朝前 */
#define ATT_ACC_SIGN     (+1.0f)
```

标定方法见 §11.2，**不用改硬件、不用重新生成工程**，改宏重编译即可。

## 4. 通信协议设计

### 4.1 帧格式（固定 9 字节）

| 字节 | 名称 | 取值 | 说明 |
|---|---|---|---|
| 0 | HEAD1 | `0xAA` | 帧头1 |
| 1 | HEAD2 | `0x55` | 帧头2 |
| 2 | LEN | `6` | 从 LEN 到 MODE 的字节数 |
| 3 | PAN_H | 0～7 | 水平角 ×10 的高字节 |
| 4 | PAN_L | 0～255 | 水平角 ×10 的低字节（0～1800 → 0～180.0°） |
| 5 | TILT_H | 0～7 | 俯仰角 ×10 的高字节 |
| 6 | TILT_L | 0～255 | 俯仰角 ×10 的低字节 |
| 7 | MODE | 0 / 1 | 0 = 电位器控制，1 = 陀螺仪姿态控制 |
| 8 | CHK | — | `LEN..MODE` 共 6 字节逐字节异或 |

设计考虑：

- **固定长度**：接收端不用缓存不定长数据，状态机极简，出错概率低。
- **双字节帧头**：0xAA 0x55 连续出现才认帧头，杜绝了单字节 0xAA 出现在数据里造成误同步。
- **0.1° 分辨率**：SG90 本身精度远达不到 0.1°，但用 ×10 可以避免"角度取整"带来的台阶感，也便于以后换数字舵机。
- **异或校验**：9 字节帧用 CRC 有点浪费，异或足以挡住蓝牙偶发误码。校验错就丢帧，等下一帧（20ms 后），不会造成卡死。
- **MODE 放在帧里**：控制方式的切换由主控端决定并随帧下发，从机"无状态"，不用额外握手。
- **带宽**：9 字节/20ms = 450 B/s。115200 8N1 理论上限 11520 B/s，占用约 **3.9%**，余量充足。

### 4.2 接收状态机（两端共用同一份 `protocol.c`）

```
WAIT_H1 ──收到0xAA──> WAIT_H2 ──收到0x55──> BODY(收满9字节)
   ^                     │                      │
   │                     └ 收到别的字节 ─────────┘
   └──────────── 校验(LEN + XOR)失败 / 收完一帧 ────────┘
```

`protocol.c`、`protocol.h` 在 master 和 slave 里是**完全相同的两个文件**，保证两端协议实现绝对一致（少一个"两边理解不一致"的坑）。

## 5. 主控端软件设计

### 5.1 任务划分（`master/Core/Src/app.c`）

| 任务 | 周期 | 优先级 | 栈(words) | 职责 |
|---|---|---|---|---|
| SensorTask | 10 ms | AboveNormal | 256 | 读 MPU6050（I2C1），姿态解算，算出陀螺仪模式下的云台目标角 |
| AdcTask | 20 ms | Normal | 128 | 读两个电位器，滤波后映射成 0～180° |
| SendTask | 20 ms | Normal | 128 | 按当前模式选角度源 → 组帧 → USART1 发蓝牙 |
| KeyTask | 20 ms | Normal | 128 | PA0 按键扫描+消抖，切换控制方式 |
| LedTask | 50 ms | Low | 128 | LED 指示（见下表） |
| DbgTask | 250 ms | Low | 192 | USART2 打印状态（轴向标定、查问题用） |
| defaultTask | — | Normal | 128 | CubeMX 生成的默认任务，保留空转 |

六个任务都用 `osDelayUntil()` 做**绝对时刻**周期调度，并带"落后太多就重新对齐"的保护，避免某次阻塞后出现"追赶式连发"。

### 5.2 共享数据与互斥

两种控制方式的角度来源不同，但都要交给 SendTask 下发，所以放在一个共享结构体里，用一把互斥锁（`osMutexNew`）保护：

```c
typedef struct {
    uint8_t mode;        /* 0=电位器 1=陀螺仪 */
    uint8_t imu_ok;      /* MPU6050 是否正常 */
    float   pot_pan, pot_tilt;    /* AdcTask 写 */
    float   gyro_pan, gyro_tilt;  /* SensorTask 写 */
    float   yaw_raw, pitch_raw;   /* 调试用 */
    float   pan, tilt;            /* SendTask 写：实际下发值 */
} app_state_t;
```

- 写：`lock(); ... ; unlock();`
- SensorTask 内部用**任务私有副本** `imu_ok`，只在状态变化时才加锁发布，减少锁竞争。
- 取角度：`app_get_cmd()` 内部加锁，SendTask 一次拿到 `pan/tilt/mode` 三个值，保证是**同一时刻的一致快照**（不会出现"角度是新的、模式是旧的"）。

### 5.3 姿态解算（`attitude.c`）

GY-521 配置：±250°/s（131 LSB/(°/s)）、±2g（16384 LSB/g）、DLPF 44Hz、采样率 100Hz，一次读 14 字节（软件 I2C @100kHz 约 1.5ms）。实测这颗模块的 `WHO_AM_I = 0x70`（**是 MPU6500 兼容芯片**，不是 0x68），所以驱动里对 ID 做了宽松判定。

**（1）陀螺仪零偏校准**：上电后连续采 200 次角速度求平均作为零偏（约 0.4s，期间面包板要静止）。零偏是陀螺积分漂移的主因，必须扣掉。若校准得到的零偏大得离谱（>20°/s，说明校准时在动），会把 `calibrated` 标志清 0，任务里 1s 后自动重试。

**（2）水平旋转（yaw）—— 陀螺仪积分**：

```
yaw += gyro_yaw * dt          （dt 由 osKernelGetTickCount() 实测，不用固定值）
```

没有磁力计，纯积分长期会漂，因此提供 `attitude_rebase()`：每次**切换进陀螺仪模式**时把当前姿态设成零位，云台同时回到中位 90°，这样：
- 误差不会累积到下一次演示；
- 云台总有一个对称的 ±88° 行程可用。

另外加了**静止死区**（角速度 < 0.8°/s 时按 0 处理），手持不动时不会缓慢爬行。

**（3）俯仰（pitch）—— 互补滤波**：

```
pitch = α · (pitch + gyro_pitch·dt) + (1-α) · atan2(-fwd, up)·57.3     α = 0.98
```

陀螺积分短期准、有漂移；加速度计测重力方向长期准、但抖动大。互补滤波把两者按 0.98 : 0.02 融合：既跟得上动作，又不会越飘越远。当加速度合成幅值 < 0.3g（剧烈甩动/自由落体）时**跳过修正**，防止用错的"重力方向"把角度带偏。

**（4）映射到云台角度**：

```
pan_cmd  = 90 + YAW_GAIN  · yaw      →  限幅到 90±88 = 2° ~ 178°
tilt_cmd = 90 + TILT_GAIN · pitch    →  同上
```
增益默认 1:1（面包板转多少度、云台转多少度）。限幅是防止指令超出舵机机械行程，把舵机顶在限位上"嗡嗡"叫。

### 5.4 控制方式切换（KeyTask）

- PA0 内部上拉，**按下为低**；每 20ms 采样一次，连续 3 次（60ms）状态一致才认为是有效动作 —— 机械按键抖动一般在 10ms 量级，60ms 消抖足够可靠。
- 切到陀螺仪模式时调用 `attitude_rebase()` 把当前姿态置零，云台从 90° 中位开始跟随（不会"一跳"）。
- **IMU 异常时拒绝切到陀螺仪模式**（保持在电位器模式），否则云台对着纹丝不动的面包板毫无反应，会被误判成"程序死了"。此时 LED 用"**双闪两下 + 长停**"报警，一眼看出是 MPU6050 没插好。

**主控端 LED 状态码**（板载 PC13，低电平点亮，无调试串口时全靠它判断）：

| 闪烁方式 | 含义 |
|---|---|
| 亮 500ms / 灭 500ms（慢闪） | 电位器模式，IMU 正常 |
| 亮 100ms / 灭 100ms（快闪） | 陀螺仪模式 |
| **闪两下、停一下**，周期 400ms（双闪） | **MPU6050 异常**（没插好/线序错），此时按键无法切到陀螺仪模式 |

> 之所以把"IMU 异常"做成双闪，是因为它和"陀螺仪模式快闪"如果都用 100ms 单闪就分不清 —— 上电时到底是进了陀螺仪模式还是 IMU 没插好，会直接误导排查方向。
- IMU 掉线后每 1s 自动重试初始化，**插好就能自己恢复，不用复位单片机**。

## 6. 舵机执行端软件设计

### 6.1 任务划分（`slave/Core/Src/app.c`）

| 任务 | 周期 | 优先级 | 栈(words) | 职责 |
|---|---|---|---|---|
| ServoTask | 20 ms | AboveNormal | 128 | 取队列里最新目标角 → 限速逼近 → 写 TIM3 两路 CCR |
| ParseTask | 轮询 | Normal | 192 | 从 USART1 收字节 → 协议状态机 → 完整帧投递队列 |
| LinkTask | 100 ms | Low | 128 | 监视"多久没收到帧"，>200ms 判失联 |
| LedTask | 50 ms | Low | 128 | 慢闪=通信正常，快闪=失联 |
| DbgTask | 250 ms | Low | 192 | 打印收到的帧数/校验错/角度 |
| defaultTask | — | Normal | 128 | CubeMX 默认任务，空转 |

### 6.2 PWM 参数推导（SG90）

SG90 是 50Hz PWM：**0.5ms→0°，1.5ms→90°，2.5ms→180°**。

```
TIM3 时钟 = 72MHz
PSC = 71        →  72MHz / (71+1) = 1MHz，即 1 个计数 = 1µs
ARR = 19999     →  20000µs = 20ms = 50Hz
Pulse(CCR) = 500 ~ 2500，直接就是"高电平微秒数"
```

所以角度→比较值的换算就是一条直线：

```c
ccr = 500 + deg * (2500-500)/180
```

代码里用 `__HAL_TIM_SET_COMPARE()` 改 CCR，**不关中断、不重启定时器**，改完立即在下一个周期生效，不会产生 PWM 毛刺。

### 6.3 转速限制（为什么需要）

`servo_update(dt)` 里限制每周期最多走 `SERVO_SLEW_DPS · dt`（默认 **300°/s**）：

- SG90 空载约 0.1s/60°（≈600°/s），限到 300°/s 既跟得上手上的动作，又不会让内部塑料齿轮猛冲猛停；
- 协议帧 20ms 一帧，如果直接写目标值，一旦丢帧再恢复会出现"跳变"，限速后表现为平滑过渡，演示时观感也更好；
- 限速还顺带解决了"云台上电瞬间从任意位置猛甩到 90°"的问题。

### 6.4 消息队列解耦（为什么用队列）

```
ParseTask ──(osMessageQueuePut, 帧)──> [队列深度4] ──(osMessageQueueGet)──> ServoTask
```

- **解析是突发的**：每 20ms 来 9 个字节（0.78ms 内到齐）；**舵机是周期的**。用队列把两者解耦，ServoTask 永远只在固定时刻被唤醒，不会被串口的时序抖动带得一起抖。
- ServoTask 每周期把队列里积压的帧**全部取空、只保留最后一帧**：这样即使某一拍被耽误，舵机也直接跳到最新角度，而不会"补做"几个过期动作。
- 队列满（深度 4 = 80ms 的量）说明系统严重超载，直接丢帧，下一帧 20ms 后又来。

### 6.5 失联保护

`LinkTask` 每 100ms 计算 `age = now - last_rx_tick`：

- `age < 200ms` 且收到过帧 → `link_ok = 1`，LED 慢闪；
- 否则 → LED 快闪，**舵机保持当前角度不动**。

"保持不动"是刻意的选择：舵机端着云台，失联时突然回中或断电松脱，比停在原地更危险也更难看。上电后一直没收到帧也归为失联（`s_ever_rx` 标志），所以从机单独上电时 LED 会一直快闪，这是**正常现象**，等主机上电就会转慢闪。

### 6.6 串口接收方式的选择（轮询 vs 中断）

本工程用 **轮询接收**（`HAL_UART_Receive()` 超时 5ms）而不是接收中断 + 环形缓冲，原因：

1. CubeMX 生成的 USART1 中断优先级默认是 0，而 FreeRTOS 要求"调用 RTOS API 的中断"优先级必须 ≥ `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`(5)。用中断还得在代码里强制改 NVIC 优先级，多一处容易忘的坑。
2. 帧长固定、速率极低（450 B/s），轮询完全跟得上：ParseTask 在 5ms 超时里等待，字节一到立刻返回，9 个字节在 0.78ms 内收完；没有数据时它被 `osDelay` 让出 CPU（优先级与 ServoTask 同为 Normal，时间片轮转，不会饿死别的任务）。
3. 轮询代码里显式处理**串口溢出**：一旦 `HAL_UART_Receive()` 返回 `HAL_ERROR`（ORE 置位），必须 `__HAL_UART_CLEAR_OREFLAG()` 清标志，否则此后永远收不到数据 —— 这是 HAL 轮询接收最容易踩的坑，代码里已经处理并计入 `err_cnt`。

## 8. 开发过程中遇到的问题与解决

| # | 现象 | 原因 | 解决 |
|---|---|---|---|
| 1 | 主控端 `.ioc` 里 ADC 配成"扫描 + 2 个规则通道 + DMA"再生成，PA4 一直没有数据 | 生成出来的 `hadc1.Init.NbrOfConversion = 1` 却配了 Rank1/Rank2，扫描位被置灰，第二个通道从来没被采样 | 改成 **ADC1/ADC2 两个独立 ADC、各自单通道连续转换、不用 DMA/扫描**。任务里直接读 DR，代码更简单也不会互相抢总线 |
| 2 | CubeMX 图形界面上 PB6/PB7 没有"变绿"，怀疑 I2C 引脚没配 | 本工程勾了 *Generate peripheral initialization as pair of .c/.h files*，所以 `HAL_I2C_MspInit`（PB6/PB7 复用开漏 + I2C1 时钟）**生成在 `Core/Src/i2c.c` 里**，而不是 `stm32f1xx_hal_msp.c` | 核查确认引脚和时钟已经在 `i2c.c` 里配好，**代码不需要自己再配**；同时删掉了我一开始多加的 `i2c1_msp.c`，否则 `HAL_I2C_MspInit` 会符号重复导致链接失败 |
| 3 | 用命令行生成从机工程时，CubeMX 启动后没有任何输出、也不生成文件 | ① 脚本里写的是 `generate code`，而这个版本的**正确语法是 `generate code <path>`**（会回显 `Usage: generate generate code <path>`）；② CubeMX 需要写自己的数据库/锁/首选项（在工程目录之外），被沙箱挡住时会静默退出 | 改成 `generate code <路径>` 并让它以完整权限运行，日志末尾出现 `Code succesfully generated` 与 `Bye bye` |
| 4 | 命令行生成的从机工程是 `Src/`+`Inc/` 扁平结构，且没有 Drivers/Middlewares/cmake | CLI 的 `generate code <path>` 按"基础结构"生成，只出 Core 文件 | 把 `Src/Inc` 归一到 `Core/Src`、`Core/Inc`，Drivers/Middlewares/cmake/启动文件从同一固件包的主控端工程复制，再按从机的外设集合改写 `cmake/stm32cubemx/CMakeLists.txt`（去掉 ADC/I2C，加 TIM3）；另外 CLI 少生成了 `sysmem.c`/`syscalls.c`/`system_stm32f1xx.c`，也一并补齐 |
| 5 | 主控端链接报 `undefined reference to 'atan2f'` | `attitude.c` 用了 `atan2f/sqrtf`，但构建命令里没有数学库 | `-lm` 必须放在目标文件**之后**；CMake 侧在 `target_link_libraries` 里加 `m` |
| 6 | 改完堆大小后 RAM 占用 88.9%，只剩 2KB | 堆一开始设 12KB，加上空闲/定时器任务静态栈和 56 个优先级就绪表，20KB RAM 快满了 | 实测任务栈合计只需约 5KB，把堆下调到 **10KB**，占用降到 78.9%，逻辑上仍有一倍余量（运行时串口可见） |
| 7 | 姿态解算每周期对 MPU6050 做两次 I2C 读 | `mpu6050_read()` 内部又调了一次 `mpu6050_read_raw()` | 抽出 `mpu6050_raw_to_data()`，一次读取同时得到原始值和物理量，I2C 流量减半 |
| 8 | 共享状态有的地方加锁、有的地方直接写 | 任务里图省事直接写 `s_st.xxx` | 统一成"任务私有副本 + 状态变化时加锁发布"，其它任务一律通过 `app_get_state()` 取快照 |
| 9 | 舵机端一上电就一直**嗡嗡响**（使劲保持、外壳发热） | 该路舵机的**信号线（杜邦线）内部接触不良**，脉宽信号时断时续，舵机内部控制环反复寻找位置 → 持续嗡响并发热 | 换一根信号线后正常。排查思路：**模拟舵机收不到 PWM 时是完全静音、输出轴可自由转动的**，会嗡嗡说明"信号进来了但位置不对" → ① 先量信号脚直流电压（3.3V × 7.5% ≈ 0.25V）确认脉宽在；② 换线；③ 拆下舵机空载通电区分机械顶住；④ 量舵机电源是否被拉到 4.5V 以下。详见 §11.3 的自检固件与 §11.4 的 SWD 读寄存器方法 |
| 10 | 主控端 MPU6050 **时好时坏、最后 100% 读不到**（HAL 报 AF 从机无应答）；两个电位器 ADC 读数稳定在满量程 3.3V（不合常理） | **面包板那一侧没有和单片机共地** —— MPU6050 和电位器由另一路电源供电，两边没有公共参考点。症状极具迷惑性：**RTOS 启动前 117 次 I2C 传输全部成功，RTOS 启动后 20/20 全部失败**，看起来像"F1 硬件 I2C 在中断环境下的时序坑" | 把面包板的 GND 与单片机 GND 连起来（共地）后立刻正常：`rd_ok=411 / rd_fail=0`、`upd_ok=310 / upd_fail=0`、`imu_ok=1`。**教训**：只要两块电路之间有信号往来（I2C/串口/ADC 采样），**必须共地**；"负载一变就失效"这类现象，先怀疑参考地/电源，再怀疑协议实现。排查过程中还把驱动改成了**软件 I2C**（GPIO 位操作），彻底不依赖 STM32F1 硬件 I2C 外设的状态机，最终 411/411 次读取零失败 |

## 10. HC-05 蓝牙配置

两个 HC-05 必须先配好（出厂默认 9600，而程序用 115200，**不改一定通信不上**）：

1. **进入 AT 模式**：按住模块上的 KEY/EN 键再上电（或 EN 接高电平后上电），此时指示灯**慢闪**（约 2s 一次），波特率固定 **38400 8N1**。
2. 用 USB-TTL 接模块（TTL_TXD→模块RXD、TTL_RXD→模块TXD、共地），串口助手 38400，勾选"发送新行"，逐条发：

| 指令 | 响应的含义 | 用在哪个模块 |
|---|---|---|
| `AT` | 回 `OK` 说明进了 AT 模式 | 两个 |
| `AT+UART=115200,0,0` | 波特率改成 115200、1 停止位、无校验 | **两个都要** |
| `AT+ROLE=1` | 设为主机 | 接主控端的那个 |
| `AT+ROLE=0` | 设为从机 | 接舵机端的那个 |
| `AT+PSWD=1234` | 配对密码（两个必须一致） | 两个 |
| `AT+CMODE=1` | 任意地址连接（免去绑定地址的麻烦） | 两个 |
| `AT+NAME=GIMBAL_M` / `AT+NAME=GIMBAL_S` | 改名字，便于在手机/电脑上分辨 | 可选 |

3. 断电重启，退出 AT 模式。主机和从机上电后会自动配对，**配对成功后两个模块的灯变成"快闪两下、停一下"**，此后就相当于一根无线串口。
4. 若配对不上：确认密码一致、`ROLE` 一主一从、两个模块距离 1m 内；实在不行用手机蓝牙搜到 `GIMBAL_S` 连一次激活。

## 11. 上电与调试步骤

### 11.1 建议按这个顺序验证（每步都失败可定位）

1. **只接 USB-TTL 到舵机端 USART2**，上电应看到：
   ```
   HEAP xxxx/10240
   LINK=0 AGE=xxxxms MODE=0 OK=0 ERR=0 | CMD 90.0 90.0 | ACT 90.0 90.0
   ```
   此时 LED 快闪、两个舵机停在中位 90° —— **正常**（还没收到帧）。
2. **烧好主控端，USB-TTL 接主控端 USART2**，上电应看到 `MODE=0 IMU=1 PAN=xx.x TILT=xx.x | POT ... | GYRO ... | YAW .. PIT .. | RAW A ... G ...`。
   - `IMU=0` → MPU6050 没插好/线序错（PB6=SCL、PB7=SDA），电路检查后再看；**没有调试串口时看 LED**：慢闪=电位器模式且 IMU 正常，**双闪两下+停一下=IMU 异常**；
   - 两个 HC-05 都上电后，舵机端的 `LINK` 应变成 `1`、`OK` 计数持续增加、`AGE` 小于 200ms；
   - 用手转电位器，舵机端的 `CMD` 数值应跟着变，舵机跟着动（**电位器模式**）。
3. **按一下主控端 PA0**，主控端 LED 变快闪、串口 `MODE=1`，舵机端 `MODE=1` —— 进入**陀螺仪模式**，云台回到中位 90° 等待跟随。
4. **做轴向标定**（见下）。
5. 拿起面包板：水平旋转 → 云台水平跟随；上下俯仰 → 云台俯仰跟随；再按一次 PA0 切回电位器模式。

### 11.2 陀螺仪轴向标定（竖直插在面包板上必做一次）

程序里默认 `YAW=gz、PITCH=gy`，竖直安装时**不一定对**。标定方法：

1. 保持 `ATT_COMP_ALPHA` 默认即可，上电后看主控端串口最后一段 `RAW A ax ay az G gx gy gz`（原始值，不滤波）。
2. **面包板水平放稳不动**：记下 `A` 三个值，数值最大的那个（≈±16000，即 1g）就是**竖直方向的加速度轴** → 填给 `ATT_ACC_UP_AXIS`（若为负值，`ATT_ACC_SIGN` 取反）。
3. **把面包板绕竖直方向（水平）转**：看 `G` 三个值里哪个变化最大 → 填 `ATT_YAW_AXIS`；向右转时该值若为负而云台转向相反，把 `ATT_YAW_SIGN` 改成 `-1.0f`。
4. **把面包板上下俯仰**：剩下变化大的那个轴填 `ATT_PITCH_AXIS`，方向不对就改 `ATT_PITCH_SIGN`。
5. **前后方向**取与第 2 步的"上"轴垂直、且指向面包板前方的那一个轴，填 `ATT_ACC_FWD_AXIS`。
6. 改完 `master/Core/Inc/attitude.h` 里的宏 → 重新编译烧录主控端即可（舵机端不用动）。

> 如果现场时间紧，可以先把 `ATT_COMP_ALPHA` 设成 `1.0`（纯陀螺积分、不做加速度修正），把 yaw/pitch 两个轴调对就能演示；演示时间短（几十秒），纯积分的漂移肉眼几乎看不出来。

### 11.3 舵机自检固件（怀疑接线 / 舵机本体时用）

正式代码里有 `APP_SELF_TEST` 开关（`slave/Core/Inc/app.h`），打开后舵机端不再解析串口，改为**分三段小幅慢摆**，用来把"程序/PWM/接线"和"机械装配/舵机本体"分开：

```powershell
cd test5\slave
# 编译自检版（不改动正式代码，只多加一个宏）
powershell -ExecutionPolicy Bypass -File .\tools\build_cli.ps1 -ExtraDefines @("-DAPP_SELF_TEST=1") -Suffix "_selftest"
# 烧进板子
.\flash\flash.ps1 -Elf .\build\cli\slave_selftest.elf
# 诊断完把正式固件烧回去
.\flash\flash.ps1
```

自检动作：每段 90°→60°→90°→120°→90°，每步 1.5s、限速 300°/s（不会硬顶限位）；LED 每步翻转一次，串口同时打印当前阶段。

| 现象 | 结论 |
|---|---|
| 能清晰摆到三个位置并安静停住 | PWM 参数与接线正常 → 问题在机械装配或供电 |
| 完全不动 | 该路信号没到（信号线/通道/舵机） |
| 一直单向旋转而不是停住 | 买到的是 **360° 连续旋转舵机**，不能用来做位置控制 |
| 只在某一处一直嗡嗡、外壳发烫 | 该位置被机械顶住（装配没对中）或该路舵机本体异常 |
| 自检正常但正式固件不跟随 | 问题在蓝牙/协议/主机侧，不是舵机端 |

> 判断"嗡嗡响"性质的关键：**模拟舵机收不到 PWM 时是完全静音、输出轴可自由转动的**。会嗡嗡说明它收到了有效信号并在使劲保持位置，所以先怀疑"到不了位"（机械）和"撑不住"（供电），而不是先怀疑程序。

### 11.4 不用示波器验证 PWM：直接从 SWD 读寄存器

ST-Link 接着的时候，可以直接把定时器寄存器读出来看它到底在命令舵机多少微秒：

```powershell
openocd -s <openocd脚本目录> -f flash\openocd_bluepill.cfg -c "init; halt; mdw 0x40000428 2; mdw 0x40000434 2; resume; exit"
```

| 地址 | 寄存器 | 期望值 |
|---|---|---|
| `0x40000428` | TIM3_PSC | `71`（0x47）→ 1µs 分辨率 |
| `0x4000042C` | TIM3_ARR | `19999`（0x4E1F）→ 50Hz |
| `0x40000434` | TIM3_CCR1 | 当前水平脉宽（µs），1500 = 中位 |
| `0x40000438` | TIM3_CCR2 | 当前俯仰脉宽（µs） |

这招能把"单片机命令了多少"和"舵机为什么不听话"彻底分开，是本次调试中定位问题最快的一步。

### 11.5 硬件自检固件（判断"引脚上到底接没接东西"）

不接串口、也没有示波器时，可以编一个自检版本 `-DAPP_HW_PROBE=1`（正常固件里这些代码不参与编译），它在上电时做两件事，结果放进全局变量，用 SWD dump 出来看：

```powershell
cd test5\master
powershell -ExecutionPolicy Bypass -File .\tools\build_cli.ps1 -ExtraDefines @("-DAPP_HW_PROBE=1") -Suffix "_probe"
.\flash\flash.ps1 -Elf .\build\cli\master_probe.elf
# 诊断完烧回正式固件
.\flash\flash.ps1
```

**（1）引脚探针**：把 PA1/PA4 临时改成"输入 + 内部上拉"和"输入 + 内部下拉"各读一次（随后恢复模拟输入交回 ADC）：

| 上拉读数 | 下拉读数 | 结论 |
|---|---|---|
| 1 | 0 | 引脚**悬空**（什么都没接） |
| 0 | 0 | 接到低阻的**低电平**（电位器滑臂在 GND 端，或直接短到 GND） |
| 1 | 1 | 接到低阻的**高电平**（滑臂在 3V3 端） |

同一招测 PB6/PB7：GY-521 板上有 4.7k 上拉，**若模块在位且有电，内部下拉压不过它 → 下拉读数仍是 1**，可据此判断"模块有没有接、有没有供电"。

**（2）I2C 扫描**：扫 `0x08~0x77` 全部地址，结果位图放在 `g_i2c_scan`，另外单独确认 `0x68` 与 `0x69`（MPU6050 的 AD0 拉高时地址会从 0x68 变成 0x69）。

**结果怎么读**：`flash/dump_live.cfg` 里已经带了对应的 `dump_image`，读出来的 `_s_st.bin` / `_rcc.bin` 等文件按 §11.4 的方式解析即可。本次调试就是用这套方法确认了"ADC 外设、I2C 外设、两个串口全部正常，问题在面包板侧没供电"。

## 14. 我是如何使用 AI 完成本题的

（对应提交要求2：与 AI 对话的关键内容截图存放在 `AI对话记录/` 目录，截图清单见该目录下的说明文件。）

### 14.1 AI 在本项目中实际承担的工作

- 用自然语言描述需求 → 由 AI 直接写出并维护 **CubeMX 的 `.ioc` 配置文件**（主控端/从机端），我负责在 CubeMX 里打开、生成代码、上板验证；
- 由 AI 完成 **协议设计、姿态解算（互补滤波/零轴校准/死区）、舵机限速、FreeRTOS 任务划分与优先级/栈预算**，并写成完整可编译的 C 代码；
- 由 AI 搭建 **编译/烧录脚本**（直连 gcc 的 `build_cli.ps1`、OpenOCD 的 `flash.ps1/probe.ps1/debug.ps1`）；
- 出错时把**报错原文/串口现象**贴给 AI 定位（例如 I2C 引脚到底有没有被生成、链接缺 `-lm`、RAM 占用偏高等）。

### 14.2 我（人）做的判断与决策

- 硬件选型与接线（两块蓝丸、两个 HC-05、独立 5V 舵机电源、共地、加滤波电容）；
- 确定"两个电位器 + 陀螺仪 + 按键切换"的交互方式，以及**失联时舵机保持不动**这一安全策略；
- 发现界面上 PB6/PB7 没变绿 → 让 AI 去核实生成的代码里 I2C 到底配没配（结论是配了，在 `i2c.c` 里），避免了一次无谓的返工；
- 现场标定陀螺仪轴向（改宏重编译），AI 无法替代手上这几下动作；
- 所有上板现象与实测数据由我确认后反馈给 AI。
